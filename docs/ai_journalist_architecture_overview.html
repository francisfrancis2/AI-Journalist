AI Journalist Architecture Overview

Current-state architecture of the AI Journalist application, based on the live codebase. This report covers the frontend, backend, LangGraph orchestration, all agents, benchmark corpora, storage layers, external services, and deployment topology across local Docker and Fly.io.

1. Executive Summary

AI Journalist is a full-stack documentary-production application. It starts from a story topic, runs a multi-agent research and writing pipeline, stores intermediate artifacts in Postgres JSON fields, uploads final scripts to S3-compatible storage, and exposes both editorial and benchmark scoring back to the user.

Core architectural idea: the app treats each story as a persisted workflow instance. The FastAPI backend launches long-running background jobs, streams status updates to the frontend, and writes every major artifact back into the stories table so the UI can resume work, branch revisions, and run follow-up research.

Primary user path

New Story -> research pipeline -> final script -> evaluation -> manual rewrite or targeted follow-up research.

Primary admin path

Admin Console -> user management -> benchmarking console -> corpus health, reference docs, rebuild orchestration.

Local environment

Docker Compose runs frontend, backend, local Postgres, and LocalStack. Neon is not required locally.

Fly environment

Frontend and backend deploy as separate Fly apps. Hosted Postgres is expected via DATABASE_URL, designed for Neon.

3. Product Surfaces

3.1 User-facing pages

  • / New Story workspace: topic entry, tone selection, target duration, live pipeline progress.
  • /research Story-specific research workspace with focused follow-up research and source browser.
  • /benchmarking Script-scoring workspace with benchmark metrics and heuristic-driven improvement actions.
  • /history Story archive with filters, download, and delete actions.
  • /results/[id] Final script view, evaluation tabs, and rewrite entry point.
  • /results/[id]/evaluation Detailed editorial quality breakdown.
  • /profile and /change-password account lifecycle screens.

3.2 Admin-only pages

  • /admin Admin Console with sub-tabs for User Management and Benchmarking Console.
  • User Management calls admin-only routes to create and delete users.
  • Benchmarking Console shows corpus health, reference inventory, stale status, and rebuild controls.
  • Admins still use the same standard /benchmarking workspace as regular users for script benchmarking.

The shared frontend shell is built in Next.js App Router. AuthGuard blocks access to all pages except login and registration, and forces non-admin users through a password-change step when their account has must_change_password set.

5. Backend Architecture

5.1 Application bootstrap

  • backend/api/main.py creates the FastAPI app, mounts routers, enables CORS, and applies trusted-host controls.
  • On startup, the backend runs Alembic migrations against non-SQLite databases and seeds the configured admin user.
  • /health is left reachable for Fly health checks through a selective trusted-host bypass.

5.3 Auth and input controls

  • JWTs are minted on login and verified through get_current_user.
  • Stories, research, and benchmarks routes require an authenticated user at the router level.
  • Admin-only actions layer get_admin_user on top of general auth.
  • User topic and chat inputs pass through security validators that reject code snippets and architecture-probing prompts before any LLM call.

7. Story Lifecycle and Revision Flows

7.1 Initial story generation

  1. User submits topic, tone, duration, and default audience from the New Story page.
  2. The backend creates a stories row with status pending.
  3. A FastAPI background task runs the compiled LangGraph pipeline.
  4. Each completed node updates the story status, and the final pipeline pass persists research, analysis, storyline, evaluation, benchmark, script audit, and script JSON back to the database.
  5. The frontend watches status through polling and the story events stream.

7.2 Focused research and regeneration

  1. The Research page starts a background focused-research job for a selected story.
  2. FocusedResearchAgent uses the existing story, audit, benchmark, and source context to decide which sources to query.
  3. Returned sources are deduplicated and merged into story.research_data; the latest focused run is stored separately for UI recovery.
  4. The user can then trigger script regeneration, which re-runs analysis, storyline creation, evaluation, benchmark scoring, scriptwriting, and script audit from the updated research set.

7.3 Rewrite and recommendation flows

  1. Audit-driven rewrite clones the story into a new revision row and runs ScriptEvaluator -> ScriptRewriter -> ScriptEvaluator.
  2. Implement Recommendations also clones the story, creates a synthetic audit from selected recommendations, then reuses the rewrite path.
  3. Revision lineage is tracked via parent_story_id and revision.
  4. Previous script snapshots are stored in script_versions for comparison in the UI.

10. Benchmarking Subsystem

Benchmarking 2.0 is a dedicated subsystem rather than a small add-on. It has its own reference corpus tables, per-library caches, admin health reporting, and a separate corpus-builder agent.

Supported libraries

Business Insider, CNBC Make It, Vox, and Johnny Harris.

Production scoring view

A combined benchmark corpus synthesized from all active component libraries.

Refresh policy

Admin-triggered refresh can rotate the freshest 25% of each healthy corpus.

10.1 Benchmarking flow

  1. CorpusBuilderAgent fetches documentary-length videos from a configured channel ID or handle.
  2. It retrieves transcripts, extracts DocStructure with Claude Haiku, and persists reference docs.
  3. Claude Sonnet synthesizes cross-corpus patterns into a versioned BIPatternLibrary.
  4. The BenchmarkAgent uses the active combined library during story evaluation.
  5. The frontend exposes both user-facing benchmark scoring and admin-facing benchmark health operations.

10.2 Reliability guardrails

  • Library health tracks freshness, readiness, cache presence, and minimum document counts.
  • If a corpus is missing or below the minimum size, admin status recommends a rebuild.
  • Missing transcripts or failed structure extraction are surfaced in rebuild error messages.

11. Deployment Topology

11.1 Local Docker topology

  • frontend: Next.js app on port 3000.
  • backend: FastAPI app on an internal port 8000.
  • db: local Postgres 16 container.
  • localstack: S3 emulation with bootstrap bucket creation.

The backend service in docker-compose.yml explicitly overrides DATABASE_URL to point at the internal db container, which means local Docker runs without Neon.

11.2 Fly.io topology

  • aijournalist-backend: Python + Playwright image, health-checked at /health, sized for Playwright memory needs.
  • aijournalist-frontend: standalone Next.js runtime that proxies API traffic to the backend Fly app.
  • GitHub Actions deployment sets Fly secrets directly, including DATABASE_URL.
  • Hosted Postgres is expected through Fly secrets; the intended provider is Neon.

12. Operational Controls, Observability, and Failure Modes

  • Story runs are resilient to navigation because long-running work is launched as backend background tasks rather than kept inside the browser.
  • The story events endpoint streams periodic snapshots until a story reaches completed or failed.
  • Every graph node is wrapped with error logging, and terminal failures are written into stories.error_message.
  • Benchmark rebuild state is tracked in an in-process build-state object so the admin UI can show running, finished, and failed rebuilds.
  • Migrations run automatically on startup for non-SQLite environments, reducing drift between deployed code and database schema.
  • Trusted-host middleware includes a Fly-specific bypass for health endpoints because Fly health probes may send raw machine IPv6 addresses as the Host header.

Current architectural dependency to watch: story quality depends on multiple external providers remaining healthy at once: Anthropic, Tavily, NewsAPI, Alpha Vantage, and the benchmark corpus sources. The product architecture is designed to degrade gracefully in some places, but missing credentials or upstream failures still directly affect functionality.
